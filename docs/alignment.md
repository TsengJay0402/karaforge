# 對齊演算法

KaraForge 的核心工作是回答一個問題：**歌詞裡的每一個字，是在第幾毫秒開始唱的？**
這份文件說明系統怎麼回答、為什麼這樣設計，以及每個可調參數的意義。實測的準確度在
[`benchmark-report.md`](benchmark-report.md)，各對齊器的比較與預設值的由來在
[ADR 0006](adr/0006-aligner-choice.md)。

程式碼在 `engine/karaforge/align/`（演算法本身，不依賴任何模型）與
`engine/karaforge/adapters/aligners/`（把模型包成對齊器）。

## 總覽

```
人聲軌 vocals.wav ──► ① 特徵        能量、人聲活動區段、起音點（10 ms 一格）
                      ② 粗對齊      每一「行」歌詞大概在哪個時間窗
                      ③ 細對齊      在各自的時間窗裡，把每個「字」放到時間上
                      ④ 精修        離開靜音、吸附起音點、補救沒有證據的字、排序、結束時間、長音
                      ⑤ 信心度      每個字 0–1 的分數
```

為什麼不直接把整首歌丟給強制對齊模型？因為一首歌有前奏、間奏、重複的副歌，模型也會聽錯；
整首一起對齊時，某一處的錯誤會把後面全部往前或往後推。先把每一行錨定在自己的時間窗裡，
錯誤就只會留在那一行。

對齊的單位是 **token**：一個漢字、一個假名、一個韓文音節，或一個以空白分隔的拉丁字母詞
（[ADR 0003](adr/0003-token-model.md)）。

## ① 特徵（`align/features.py`）

在 16 kHz 的人聲軌上，每 10 ms 計算：

- **能量**（RMS，dB）。
- **人聲活動**：夠大聲，而且夠「有音高」（頻譜平坦度低）。平坦度的條件是為了排除分離後殘留的鼓聲。
  相鄰的活動影格合併成區段，間隔 300 ms 以內的區段相連。
- **起音點**：對數梅爾頻譜的 spectral flux（只算上升的部分）取峰值，再沿著上升的斜坡往回走到開始上升的地方——
  一個字是從聲音「開始變大」的那一刻開始的，不是變化最快的那一刻。

另外用 librosa 估計 tempo 與拍點，供倒數提示使用。

## ② 粗對齊：行層級錨定（`align/coarse.py`）

每一行得到一個時間窗，來源依可靠程度排列：

| 來源 | 說明 |
|---|---|
| `anchor` | 這一行有使用者鎖定（`locked`）的字：直接由鎖定的時間推出時間窗。 |
| `hint` | 歌詞是從 LRC／SRT／ASS 匯入的，檔案裡有這一行的時間。 |
| `asr` | 語音辨識的逐詞時間與歌詞比對成功。 |
| `regions` | 比對不到；這一段未錨定的行數剛好等於人聲活動區段數，一行一段。 |
| `interpolated` | 比對不到；在前後已錨定的行之間，依字數比例分配有人聲的時間。 |

### 與語音辨識結果比對

語音辨識（Whisper）在歌聲上常常聽錯字，但通常「聽起來差不多」。所以比對不是在文字上做，
而是在**羅馬拼音的字母序列**上做：

1. 歌詞與辨識結果都轉成不帶聲調的拼音字母（中文先轉簡體再查 pypinyin；英文直接用字母；假名轉羅馬字）。
   「請請慢慢聊起來」與「星星慢慢亮起來」在大部分位置仍然對得上，而且完全不需要中文斷詞。
2. 用 Levenshtein 對兩個字母序列做全域對齊，每個歌詞字母因此對應到一個辨識字母，也就得到一個時間。
3. 一行裡「至少一半字母完全吻合」的 token 算是命中；取時間上最密集的一串命中來決定時間窗
   （單獨一個落在半分鐘之外的命中不會把時間窗拉長）。
4. 命中率太低的行不採用辨識結果，改由 `regions`／`interpolated` 補上。整首歌的命中率太低時，
   辨識結果全部不用。
5. 違反行順序的時間窗會被拿掉（保留比對品質比較好的那一個；鎖定的錨點永遠保留）。

### 先清理辨識結果的時間

辨識模型的逐詞時間有幾種固定的毛病，直接拿來用會把一整行錨到錯的地方（`clean_words`）：

- **塌陷的幻覺**：模型在沒有根據的地方「背出」歌詞時（歌詞被當成提示詞餵給它），一連串的詞會擠在同一個時間點、
  長度為零。連續三個以上這樣的詞是物理上不可能的，直接丟掉。
- **跨過停頓的詞**：一句的第一個詞常常被往前拉過整段間奏。這種詞只相信它的結束時間，開始時間改成人聲回來的地方。
- **掉進停頓裡的詞**：整個詞被放在沒有人聲的地方，而且它和下一個人聲區段之間沒有別的詞——移到那個區段的開頭。
- 一串時間正常的詞即使落在「人聲活動偵測認為是靜音」的地方也不去動它：
  在訊噪比很差的混音裡，偵測器漏掉小聲的演唱比辨識器連續猜對時間更常發生。

## ③ 細對齊：字層級（`align/fine.py`）

每一行在自己的時間窗前後各加 `window_pad_ms`（預設 1 秒）的範圍內對齊。

- **鎖定的字把一行切成幾段**：兩個鎖定的字之間的字，只會在這兩個時間之間對齊。
  其他行的鎖定時間也會限制這一行的範圍。這就是「修正三個字，其餘自動變準」的機制。
- **鄰行的聲音**：加了前後 1 秒之後，時間窗裡可能聽得到上一行的尾巴或下一行的開頭。
  細對齊會告訴對齊器這件事（`open_start`／`open_end`），並附上鄰行最靠近的幾個字（`context_tokens`，預設 4）當作上下文。
  只有在鄰行的時間窗確實伸進來、或時間窗邊緣確實有人在唱的時候才會這樣做——
  如果時間窗是從靜音開始的，就不該給對齊器「前面那段聲音可以忽略」的自由。
- **記住答案**：同一個對齊器、同一段音訊、同一串字的問題只問一次。使用者鎖定幾個字後重新對齊時，
  只有邊界改變的那幾段會重新送進模型。

### 對齊器

所有對齊器都實作同一個介面（`Aligner`，見 [`adapters.md`](adapters.md)），用 `align.aligner` 選擇。

#### `ctc`（預設）

wav2vec2 的 CTC 模型每 20 ms 輸出一次「現在是哪個符號」的機率；強制對齊就是用 Viterbi 找出把已知的符號序列
鋪到這些影格上的最佳方式（`align/ctc.py`，純 numpy）。幾個針對歌聲的設計：

- **同音字合併**：中文模型的符號是幾千個漢字，而它在歌聲裡常常把字聽成另一個同音字。
  所以不問「『星』在哪裡」，而是問「讀作 *xing* 的任何一個字在哪裡」——把所有同音字的機率加起來，把模型當成音節辨識器來用。
- **兩個模型，一張格子**：中文字用中文模型（`wav2vec2-zh`），其他的字用英文模型（`wav2vec2-en`）。
  兩個模型的影格完全對齊（都是 20 ms 一格），所以中英混雜的一行可以放在同一次 Viterbi 裡，
  每個字各自從會拼它的模型取機率。
- **分隔符號算空白**：模型在字與字之間會輸出詞分隔符號 `|`；對齊時把它併進 blank。
- **萬用符號**：時間窗的開頭或結尾可能有鄰行的聲音時，在序列兩端各加一個「任何非空白的聲音」符號把它吸收掉；
  模型拼不出來的字（沒有對應符號）也用它。
- **整首歌只跑一次模型**：聲學模型的輸出與歌詞無關，所以整條人聲軌只計算一次，每一行只是切出自己那一段來做 Viterbi。
  重新對齊幾乎不花時間。
- **修正固定的延遲**：CTC 的輸出尖峰落在音節開始之後（中文模型約 30 ms、英文模型約 80 ms），回報時間前先扣掉。
- **分數的意義**：不是「模型認出這個字的機率」（唱出來的字常被聽成別的字，但位置仍然是對的），
  而是「模型在這個位置有沒有聽到一個音節」，以及「這個字是不是被硬擠在鄰字的音節旁邊」。

#### `whisper-attn`（`cpu-lite` 的預設）

把已知的歌詞餵進 Whisper 的 decoder，對交叉注意力做 DTW，得到每個 token 的時間。不需要額外的模型
（沿用語音辨識階段的 Whisper），任何語言都能用，但準確度明顯比 `ctc` 差，時間窗上限 30 秒。

#### `qwen`（選用）

Qwen3-ForcedAligner-0.6B：把音訊與「字⟨時間⟩⟨時間⟩字⟨時間⟩⟨時間⟩…」一起讀進去，一次前向計算就預測出每個時間格
（80 ms 一格）。本專案不取機率最高的那一格，而是取峰值附近的機率加權平均，得到比 80 ms 更細的時間；
峰值附近的機率總和就是分數。需要另外安裝 `qwen-asr` 套件（`uv sync --extra qwen`）。

#### `hybrid`（選用）與 `auto`

兩種對齊器在開發集上錯的地方不一樣：CTC 放中文字很穩，但英文詞偏晚；Qwen 在有把握的時候放英文詞很準，
而且它「知道自己沒把握」。`hybrid` 讓每個字用擅長它的那一個，並互為備援：

| token | 平常用 | 例外 |
|---|---|---|
| 中文字 | CTC | CTC 完全沒聽到，而 Qwen 有把握 |
| 其他 | Qwen | Qwen 沒把握 |

`auto` 表示「裝了 `qwen-asr` 就用 `hybrid`，否則用 `ctc`」，是 `gpu-quality` 設定檔的預設。

## ④ 精修（`align/refine.py`）

依序執行，鎖定的字永遠不動：

1. **離開靜音**：字不可能在沒有人唱的時候開始。落在靜音裡的開始時間往後移到人聲出現的地方
   （一行的頭幾個字最多看 3 秒，行內的字最多看 1 秒，而且不會越過下一行）。
2. **起音點吸附**：開始時間移到 ±`onset_snap_ms`（預設 60 ms）內最近的起音點。同一個起音點不會被兩個字共用。
3. **沒有證據的字**：對齊器分數低於門檻的字（對齊器其實沒聽到它，只是把它塞在鄰字旁邊）
   改放到「前後兩個字之間、還沒被別的字佔用、最強的那個起音點」。起音偵測知道那裡有東西開始了，
   即使辨識模型說不出是什麼。門檻由對齊器提供（`align.weak_score` 可以覆寫，0 表示停用）。
4. **順序與最短字長**：開始時間嚴格遞增，相鄰至少 `min_token_ms`（預設 60 ms）。
5. **結束時間**：預設等於下一個字的開始；如果到下一個字之前人聲安靜超過 `pause_threshold_ms`（預設 300 ms），
   改成能量掉下去的地方，讓填色在換氣時停住。
6. **長音**：每一行最後一個字延續到人聲能量消失為止（上限 `max_tail_ms`，且不超過下一行）。

## ⑤ 信心度（`align/confidence.py`）

三種互相獨立的證據加權合成：

| 證據 | 權重 | 內容 |
|---|---:|---|
| 對齊器分數 | 0.40 | 見上面各對齊器的說明 |
| 粗細一致 | 0.35 | 最後的開始時間離語音辨識聽到這個字的時間有多近，以及這一行整體的比對品質 |
| 起音吻合 | 0.25 | 開始時間離最近的起音點有多近 |

內插出來的字（對齊器沒辦法處理的片段）固定是 0.1，鎖定的字是 1.0。編輯器依這個數字替字上色，讓使用者先看最可疑的。
這個分數有多可靠（AUROC、「只檢查信心最低的 10% 能找到多少問題」）列在評測報告裡。

## 錨點重對齊

使用者在編輯器裡修正一個字時，那個字會被鎖定。重新對齊時：

- 粗對齊：有鎖定字的行直接由鎖定時間決定時間窗，與它矛盾的辨識結果被忽略。
- 細對齊：鎖定的字是硬性邊界，只有邊界之間的片段重新計算，其餘沿用記住的答案。
- 精修：不會移動鎖定的字，其他字的順序會配合它們調整。

## 參數

全部在 `align.*` 之下，可以用 `--set align.名稱=值` 覆寫；預設值是在評測的 dev 分組上選的。

| 名稱 | 預設 | 說明 |
|---|---|---|
| `aligner` | `ctc` | `ctc`、`whisper-attn`、`qwen`、`hybrid`、`auto` |
| `coarse` | `asr` | `regions`（不用語音辨識）與 `global`（不切時間窗）只供消融實驗使用 |
| `window_pad_ms` | 1000 | 細對齊時每一行時間窗前後多留的時間 |
| `context_tokens` | 4 | 提供給對齊器的鄰行 token 數 |
| `lead_ms` | 依對齊器 | 回報時間的整體偏移修正（正值表示往前移） |
| `onset_snap` / `onset_snap_ms` | 開 / 60 | 起音點吸附與最大距離 |
| `weak_score` | 依對齊器 | 低於這個分數的字視為沒有證據；0 停用 |
| `min_token_ms` | 60 | 最短字長 |
| `pause_threshold_ms` | 300 | 超過這個長度的停頓會讓前一個字提早結束 |
| `long_note` / `max_tail_ms` | 開 / 6000 | 行尾長音延伸與上限 |

## 已知的侷限

- **轉音與拖腔**：一個字唱好幾個音的時候，系統只給這個字一個開始時間，填色在整個字的時間內等速前進。
- **英文詞的開頭**：字母層級的 CTC 模型對短的、以母音開頭的詞（is、a、I）偏晚；這是 `hybrid` 存在的原因。
- **中英混雜的行**：英文模型在拉長的中文母音上也會輸出零星的字母，行尾的英文詞偶爾會被往前吸過去。
- **和聲與疊唱**：分離模型把和聲留在伴奏裡（這是刻意的，比較像真的伴唱帶），但主唱與和聲同時唱不同歌詞時，
  對齊只會跟著主唱。
- **時間窗上限**：`whisper-attn` 30 秒、`qwen` 170 秒；超過時時間窗會被截短。
