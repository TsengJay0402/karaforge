# 歌詞格式

KaraForge 可以讀四種歌詞檔：純文字 `.txt`（最常用）、`.lrc`、`.srt`、`.ass`／`.ssa`。
也可以完全不給歌詞，讓語音辨識產生草稿（見最後一節）。

檔案編碼可以是 UTF-8（有沒有 BOM 都可以）、有 BOM 的 UTF-16、Big5 或 GB18030；讀不出來時會明確報錯，不會亂猜。

## 純文字 `.txt`

一行一句，就這樣。其餘都是選用的：

```text
# title: 夜空中的旅人
# artist: 示範樂團
# 作詞: 某某某
# language: zh-TW

[男] 車窗上的雨滴 排成一條線
[女] 夜空裡的星星慢慢亮起來

[合] 我們一起唱 la la la
這一行沒有標記，沿用上一行的演唱者
他還是重{ㄔㄨㄥˊ}複了一次
```

| 寫法 | 意思 |
|---|---|
| `# 鍵: 值` | 歌曲資訊。鍵可以是 `title`／`歌名`／`曲名`、`artist`／`歌手`／`演唱`、`lyricist`／`作詞`、`composer`／`作曲`、`language`／`lang`／`語言`。冒號全形半形都可以。其他以 `#` 開頭的行是註解。 |
| 空行 | 段落分隔。新段落前面只要停頓 2 秒以上，畫面就會清空、從上排重新開始，並顯示倒數提示（同一段落內要停頓 4 秒以上才會）。兩個門檻都可以在主題裡調整（`layout.paragraph_gap_ms`、`layout.section_gap_ms`）。如果**每一行後面都有空行**（從網頁貼來的歌詞常常這樣），空行就不代表段落，不會有這個效果。 |
| `[男]`、`[女]`、`[合]` | 演唱者，從這一行起生效，直到下一個標記。也接受 `[M]`／`[male]`、`[F]`／`[female]`、`[all]`／`[duet]`／`[both]`／`[合唱]`。標記可以單獨佔一行。 |
| `[其他名字]` | 自訂演唱者（例如 `[阿明]`）。第一次出現時自動建立，依序使用主題的男、女、合唱顏色。 |
| `字{讀音}` | 指定前一個字的讀音（破音字、台語、日文漢字…）。讀音會顯示在字的上方；如果寫的是注音或拼音，對齊時也會用它。 |

斷字規則（不需要自己處理，只是讓你知道結果）：

- 中文、日文漢字：**一個字一個單位**。
- 英文等拼音文字：**一個單字一個單位**（`don't`、`3.14` 各算一個；用連字號連起來的字在連字號處分開）。
- 假名：一個假名一個單位，小假名與長音符號（ゃ、ゅ、ょ、ー…）併入前一個假名；促音 っ 自成一個單位。
- 韓文：一個音節字一個單位。
- 標點與空白附著在前一個單位上，不會單獨計時。

從別處貼來的 LRC 時間標記（`[00:12.30]`、`<00:12.30>`）在 `.txt` 裡會被忽略；想保留時間請把檔案存成 `.lrc`。

## LRC `.lrc`

- 逐行時間 `[mm:ss.xx]歌詞`：這一行的時間會存成「行時間提示」，對齊時用來決定這一行在哪裡，行內每個字仍然由對齊器決定。
- 同一行有多個時間標記（`[00:12.30][01:40.10]副歌`）代表這句重複出現。
- 逐字時間（enhanced LRC）`[00:12.30]<00:12.30>車<00:12.75>窗<00:13.10>`：每個字的時間直接採用，並且**鎖定**——
  之後重新對齊也不會動它，除非你在編輯器解除鎖定。一個時間標記後面有好幾個字時，只有第一個字鎖定，其餘平均分配並標記為估計值。
- `[ti:]`、`[ar:]`、`[au:]` 讀成歌名、歌手、作曲；`[offset:±毫秒]` 會套用。
- 行首的 `M:`、`F:`、`D:`（男、女、合唱）會轉成演唱者。

## SRT `.srt`

每一段字幕變成一行歌詞，字幕的起迄時間成為行時間提示。HTML 與 ASS 樣式標記會被去掉。

## ASS／SSA `.ass`、`.ssa`

- KaraForge 自己匯出的 ASS：可以完整讀回每個字的時間與演唱者。
- 其他工具的卡拉 OK 字幕：`\k`、`\kf`、`\ko`、`\K` 標記會讀成逐字時間（鎖定）。
- 一般字幕：每個 `Dialogue` 變成一行，帶行時間提示。

## 匯出

`kf export --format …` 或 Web 的匯出對話框：

| 格式 | 內容 |
|---|---|
| `mp4` | 字幕燒進畫面的影片（H.264 + AAC） |
| `mkv` | 影片 + 軟字幕（ASS，字型一併內嵌）+ 兩條音軌（伴唱、原唱），播放器可以切換 |
| `ass` | ASS 字幕（可以用 Aegisub 再加工） |
| `lrc` | 逐行 LRC |
| `elrc` | 逐字 enhanced LRC |
| `srt` | SRT 字幕 |
| `ultrastar` | UltraStar 的 `.txt`（含音高；需要把媒體檔放在同一個資料夾） |
| `kfproj` | 整個專案的壓縮檔 |

LRC、enhanced LRC、SRT、ASS、UltraStar 匯出後再匯入，時間誤差不超過各格式的最小時間單位（測試 `tests/unit/test_formats.py` 驗證）。

## 沒有歌詞：語音辨識草稿

不給歌詞檔（`kf new song.mp3`、`kf auto song.mp3`，或在 Web 選「沒有歌詞，用 AI 辨識」）時：

1. 在分離出來的人聲上做語音辨識；
2. 把辨識結果整理成歌詞草稿：去掉不是唱出來的東西（`[Music]` 之類的註記、落在沒有人聲處的句子、標點），
   中文依專案語言轉成繁體或簡體（只轉字形，不改用詞），依辨識器的斷句與停頓（0.7 秒以上）切行，太長的行在最長的停頓處再切開；
3. 像一般歌詞一樣對齊。

**草稿一定要校對，而且要有心理準備它可能錯得很多。** 語音辨識對歌聲的錯誤率遠高於對說話。
我們唯一量過的例子是測試用的那首合成歌曲（43 個字，10 dB；合成歌聲對辨識器來說特別難，真人演唱沒有量測過）：

| 模型（設定檔） | 草稿的字元錯誤率 | 怎麼量的 |
|---|---:|---|
| Whisper base（`cpu-lite`） | 83.7%（43 個字錯 36 個） | 整合測試 `tests/integration/test_draft_flow.py` 的輸出 |
| Whisper small（`balanced`） | 53.5% | 對同一段人聲直接執行辨識器一次 |
| Whisper large-v3-turbo（`gpu-quality`） | 48.8% | 同上 |

也就是說，在這個例子裡**最好的模型也只對了一半**，最小的模型幾乎全錯——它產生的草稿只有「行數與位置大致正確」這個價值。
如果手邊找得到歌詞，貼上歌詞永遠比用辨識的好；沒有歌詞時請用 `balanced` 以上的設定檔。

編輯器會提醒這是草稿。改完文字後按「重新對齊」（或 `kf align`）即可，不需要重新辨識。
專案一旦有了歌詞（不論是草稿還是你貼上的），就不會再被草稿覆蓋。

實作上的一個細節：沒有歌詞提示時，Whisper 的「無語音」判斷會被關掉。那個判斷是為說話設計的，會把持續的歌聲當成靜音，
整段 30 秒的內容直接消失（上面的例子裡，前半首歌因此不見）；關掉之後多出來的「靜音裡的幻覺文字」由人聲活動區段濾掉。
