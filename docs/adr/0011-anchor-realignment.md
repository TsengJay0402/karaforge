# ADR 0011：鎖定的字怎麼用於重新對齊（演算法第 8 版）

- 狀態：已採用（取代第 7 版的做法）
- 日期：2026-11-21

## 背景

規格把「鎖定的字是硬性錨點，只對錨點之間的區段重新對齊」列為必須，並說這是半自動體驗的核心：使用者修正 3 個字，其餘自動變準。
第 7 版照字面實作：

- 有鎖定字的行，時間窗直接由鎖定的字推算（每個字假設 0.4 秒）；
- 行內被鎖定字隔開的每一段，各自拿「前一個鎖定字的結束」到「後一個鎖定字的開始」之間的音訊去對齊。

單元測試確認了鎖定的字不會被移動。**但凍結之前沒有在 dev 分組上量過它對其餘的字的影響。**

test 分組的評測顯示：鎖定 5% 的字之後，其餘的字需要修正的比例從 6.5% 上升到 7.7%（弄壞 159 個、修好 76 個）。
回到 dev 分組重做，結果相同（7.7% → 9.2%）。

## 原因

1. **時間窗變差了。** 一行原本有語音辨識給的準確時間窗；只要鎖定其中一個字，這個時間窗就被「鎖定時間 ± 字數 × 0.4 秒」取代。
   慢歌的行尾因此落在時間窗外。
2. **音訊被切在音節中間。** 對齊器需要聽到完整的音節。CTC 模型的輸出尖峰比音節的起點晚 30–100 毫秒，所以切在鎖定字邊緣的音訊，
   開頭還留著前一個字的尾巴，結尾卻少了最後一個字的證據。英文（延遲 100 毫秒）受害最重，這與觀察到的現象一致。
3. **把結束時間當成硬性邊界。** 使用者標記的是字從哪裡開始；鎖定字的結束時間通常只是先前對齊的結果，可能正是他們要修的那個錯誤的一部分。

## 決定

- 有鎖定字的行，時間窗由**鎖定的字加上與它們不矛盾的辨識結果**一起決定。位置在鎖定字錯誤一側、或遠得不合理的辨識結果才被忽略。
- 緊鄰鎖定字的那一段，**連同鎖定的字一起**交給對齊器：音訊從前一個鎖定字的開頭到後一個鎖定字的結束（至少開頭之後 0.3 秒），
  文字也包含這兩個字，只是不採用它們的對齊結果。
- 未鎖定的字只被前後鎖定字的**開始時間**限制。
- 時間窗會超過對齊器長度上限時，退回切開的做法。
- 舊行為保留在 `align.anchor_context=false`；`kf bench` 的錨點實驗固定用同一批錨點多跑一次舊行為，並在報告裡加上「同一批字、鎖定前後」的配對表，
  讓這類退步以後一眼就看得到。

所有調整只在 dev 分組上進行。沒有鎖定字時，演算法的輸出與第 7 版完全相同（test 分組 120 個音檔逐一比對過）。

## 結果

同一批未鎖定的字，鎖定前 → 鎖定後（誤差 > 150 ms 的比例）：

| | dev（2520 個 token） | test（7116 個 token） |
|---|---|---|
| 第 7 版，隨機 5% | 7.7% → 9.2%（修好 28、弄壞 66） | 6.5% → 7.7%（修好 76、弄壞 159） |
| 第 8 版，隨機 5% | 7.7% → 7.0%（修好 24、弄壞 7） | 6.5% → 6.1%（修好 42、弄壞 12） |
| 第 8 版，信心度最低的 5% | 6.5% → 5.8%（修好 22、弄壞 6） | 5.2% → 4.8%（修好 48、弄壞 18） |

## 沒有採用與還沒做的

- **依鎖定字的偏移量校正鄰字**（對齊器把鎖定字放在哪裡、使用者說它在哪裡，差多少就把鄰字移多少）：對「整段路徑漂走」的情況有效，
  但測資裡有一類字的標準答案與聽得到的起點相差 0.6 秒（ADR 0007 記錄的瑕疵），這種錨點會把鄰字帶偏。在只有 7 個失敗案例的 dev 上調這種規則，風險大於收穫。
- **把鎖定字的位置寫成 CTC 動態規劃裡的限制**（允許某個目標只能在指定的影格進入）：這是原理上正確的做法，剩下的失敗案例多半也是這一類。列為下一步。
- 這次修正只在 CTC 類對齊器上量過。`whisper-attn` 只有整合測試確認流程可以跑、鎖定的字不變。

## 要記住的事

- 這個缺陷是 test 分組的結果揭露的，所以第 8 版在 test 上的數字不是盲測。第一次的結果原樣保留在 `bench/reports/test-v1/`。
- 修正之後錨點不再有害，但幫助有限，中文是持平到略差（test：4.2% → 4.3%）。規格描述的效果目前只做到一部分。
- 錨點實驗用標準答案當作鎖定字的結束時間，這對舊做法是有利的；真實使用時舊做法會更差，但測資量不到。
