# ADR 0010：無歌詞流程與自動讀音

- 狀態：已採用
- 日期：2026-11-21

## 背景

規格要求兩個「從文字出發」的進階功能，但沒有規定做法：沒有歌詞時由語音辨識產生草稿（情境 3），以及注音／拼音（含破音字，要自建測試集並報告準確率）。
兩者都會把「機器猜的文字資料」寫進專案，所以要先決定：資料放在哪裡、什麼時候產生、怎麼不蓋掉使用者的東西。

## 決定

### 歌詞草稿

- **獨立的 `draft` 階段**，排在 `asr` 之後、`align` 之前。它只在專案沒有歌詞時執行（`is_needed`），所以使用者一旦貼上或修改歌詞，就不會再被草稿覆蓋；
  `publish` 寫入前還會再檢查一次（處理期間使用者可能已經貼了歌詞）。
- **專案格式升到第 3 版，加上 `meta.lyrics_source`（`user`／`asr`）。** 理由不只是讓編輯器能顯示「這是草稿」：
  語音辨識平常會拿歌詞當提示，如果草稿也被拿去當提示，辨識階段的快取鍵會在草稿寫入後改變，下一次處理（甚至只是匯出）就會重新辨識、重新對齊。
  有了這個欄位，草稿專案永遠不帶提示，辨識結果在校對期間一直有效。
- **草稿怎麼切行**：以辨識器的斷句為主，加上 0.7 秒以上的停頓；太短的行併入沒有被停頓隔開的鄰行；太長的行（超過 16 個中文字寬）在最長的停頓處切開。
  相隔 4 秒以上就換段，與匯入 LRC 時的規則相同。
- **清掉什麼**：擠在同一瞬間的幻覺文字、括號註記（`[Music]`）、完全落在沒有人聲的區段裡的句子、所有標點（詞內的撇號與連字號除外）。
  歌詞慣例上用空白與換行分句，辨識器的標點本來就是猜的。
- **繁簡轉換只轉字形**（OpenCC 的 `s2tw`／`s2hk`／`t2s`），不用會連詞彙一起換的 `s2twp`：草稿應該保留唱出來的字。
- **沒有提示時關掉 Whisper 的「無語音」判斷。** 實測中它把前 30 秒的歌聲整段丟掉。只有這種情況的快取鍵會改變，有提示的辨識結果維持原樣（評測用的就是那一種）。
- 草稿的每個字帶著辨識器給的粗略時間，每一行另外留下 `time_hint`：使用者把一行改得面目全非之後，對齊仍然知道那一行在哪裡。

### 自動讀音

- **讀音是存在專案裡的資料**（`ruby` 加上 `ruby_source: "auto"`），不是算繪時才臨時產生的。這是規格範例的寫法，編輯器也才看得到、改得動。
- **什麼時候產生**：中文歌詞進入專案的每一個時機——建立專案、替換歌詞、產生草稿、編輯一行文字。要不要**顯示**是主題的事（`ruby.enabled`）。
- **手動讀音永遠優先**，任何自動處理都不會動 `ruby_source: "manual"` 的字。
- **種類（注音或拼音）不另外存欄位**，由現有的自動讀音判斷，沒有的話依語言決定（`zh-TW` 注音、`zh-CN` 拼音）；`kf ruby --kind` 與編輯器可以切換。
  其他語言不自動產生（日文歌詞裡的漢字不是唸國語）。
- **引擎是查表式的**：OpenCC 臺灣字表轉簡體 → pypinyin 詞庫 → 五個虛詞（得、地、了、著、還）的前後文規則與「一」「不」變調 → 繁體字形區分 → 臺灣讀音表。
  沒有採用語言模型（g2pW 等）：準確率會更高，但要多一個數百 MB 的模型與相依套件；先把查表法做好並**量出它有多準**。
- **測試集先於引擎**：171 句的破音字測試集在引擎動工前寫好並提交，之後沒有改；引擎完成後量一次就是報告的數字（92.4%，未加自訂規則的基準 88.3%）。
  讀錯的 13 題沒有回頭修，逐題列在文件裡。
- 讀音的自訂規則是另外套在 pypinyin 的結果上的，**沒有修改 pypinyin 的全域詞庫**——對齊用的羅馬拼音化也用 pypinyin，改了會讓已經凍結的評測結果與程式不一致。

## 後果與限制

- 草稿的品質取決於辨識器，而辨識器在歌聲上表現很差：測試用的合成歌曲上，最好的設定檔字元錯誤率也有 51.2%（`balanced`；`cpu-lite` 是 83.7%，`gpu-quality` 是 60.5%）。
  文件與編輯器都把它當成「要校對的起點」來呈現。
- 查表法分不出「名詞與動詞讀音不同、而動詞單獨出現」的破音字。
- 臺灣讀音表（42 項）與破音字測試集的預期讀音都出自作者的知識，沒有逐項與辭典核對。
- 專案格式多了一版；舊專案開啟時在記憶體中升級，儲存時才寫回，並保留備份。
