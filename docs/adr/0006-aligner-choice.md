# ADR 0006：對齊器的選擇、校正與各設定檔的預設值

- 狀態：已採用
- 日期：2026-11-21

## 背景

規格要求至少兩種可切換的強制對齊器並在評測中比較，建議「Qwen3-ForcedAligner（中文首選）＋ CTC 類對齊器（CPU 輕量備選）」。
M1 只有 Whisper 交叉注意力對齊器，在開發用的合成歌上誤差中位數約 100 ms、三成以上的字需要人工修正，離目標很遠。

M2 實作了下列對齊器，並**只用評測的 dev 分組**（每種語言 4 首 × 4 種訊噪比＝48 個音檔、2652 個 token）決定校正值與預設值。
這份文件記錄所有在 dev 上做過的決定；test 分組在這些決定全部凍結之後才第一次執行。

| 名稱 | 模型 | 權重授權 | 額外套件 |
|---|---|---|---|
| `whisper-attn` | 語音辨識階段的 Whisper（交叉注意力＋DTW） | MIT | 無 |
| `ctc` | wav2vec2 XLSR-53 中文（1.2 GB）＋ wav2vec2 base 960h 英文（0.4 GB） | Apache-2.0 | 無 |
| `ctc-mms` | MMS-300M forced aligner（羅馬拼音，1.2 GB） | **CC-BY-NC-4.0** | 無 |
| `qwen` | Qwen3-ForcedAligner-0.6B（1.8 GB） | Apache-2.0 | `qwen-asr`（Apache-2.0） |
| `hybrid` | `ctc` ＋ `qwen` | Apache-2.0 | `qwen-asr` |

## 在 dev 上觀察到的事，以及對應的設計

依發現的順序：

1. **CTC 模型常把唱出來的字聽成別的字，但「有一個音節從這裡開始」很準。**
   所以中文用「同音字合併」（把讀音相同的所有字的機率加總），對齊器的分數也改成
   「模型在這個位置有沒有聽到音節、這個字是不是被硬擠在鄰字旁邊」，而不是「認出這個字的機率」。
   改之前有一半的 token 分數接近 0（其實位置是對的）；改之後 82% 的 token 分數 ≥ 0.8（其中只有 1.7% 是錯的），
   分數最低的一組集中了約六成的錯誤。
2. **模型會在字與字之間輸出詞分隔符號 `|`**，不併入 blank 的話會把字吸過去。
3. **「鄰行聲音」的萬用符號只在真的可能有鄰行聲音時才使用。** 原本每個時間窗開頭都允許，
   結果一行的第一個字被聽錯時，萬用符號把它的音節吃掉，第一個字晚了半秒以上。
4. **Whisper 以歌詞當提示詞時會「背出」歌詞**：一連串長度為零、擠在同一個時間點的詞。
   粗對齊把整行錨到那裡，是 dev 上最大的一類錯誤（中文 P95 從 780 ms 降到 132 ms 就是修這個）。
   連同「第一個詞被拉過整段間奏」等毛病，現在在比對之前先清理辨識結果的時間（`align/coarse.py` 的 `clean_words`）。
5. **CTC 的輸出有固定延遲**：中文模型的中位數約 +30 ms；英文模型的中位數約 +60 ms，
   但分布往晚的方向拖得很長（短的、母音開頭的詞晚 200 ms 以上）。回報時間前先扣掉（中文 30 ms、英文 100 ms）。
   Whisper 注意力對齊器則是偏早約 110 ms。
6. **對齊器完全沒聽到的字**（夾在兩個音節之間被吞掉的字、行尾的長音）會被塞在鄰字旁邊。
   精修時把這種字改放到鄰字之間、還沒被佔用的最強起音點（`weak_score`）。中文 P95 從 132 ms 降到 101 ms。
7. **中英混雜的行不能只用中文模型**（英文詞 68% 錯）。兩個 wav2vec2 模型的影格完全對齊，
   所以改成在同一次 Viterbi 裡讓中文字用中文模型、英文詞用英文模型，混雜行的錯誤率從 33% 降到 14%。
8. **Qwen 與 CTC 錯的地方不一樣。** Qwen 在英文詞上有把握時很準（分數 ≥ 0.9 的字只有 1% 錯），
   沒把握時（分數 < 0.3）有三分之二是錯的；CTC 在中文字上很穩，英文詞偏晚。
   `hybrid` 讓中文字用 CTC、其他用 Qwen，並互為備援。
9. Qwen 需要鄰行的字當上下文：不給的話（`context_tokens=0`）英文的錯誤率從 11% 升到 15%，還會出現 5% 的行對應錯誤。

### 選過的參數

| 參數 | 試過的值 | 選定 | 依據 |
|---|---|---|---|
| CTC 中文模型延遲 | 20／30／40 ms | 30 ms | 關掉吸附時的偏差中位數 +31 ms；三個值的結果幾乎一樣 |
| CTC 英文模型延遲 | 40／60／80／100／120 ms | 100 ms | 英文 >150 ms：15.4%／12.9%／10.2%／8.6%／8.3%；中位數 34／24／22／27／29 ms。100 之後幾乎不再改善，中位數卻繼續變差 |
| 吸附距離 `onset_snap_ms` | 40／60／80／100 | 60（不變） | 40–60 幾乎相同，100 讓 P95 變差 |
| `weak_score`（CTC） | 0／0.1／0.3／0.5 | 0.3 | 0.1–0.5 相同（中文 3.9%），0 是 4.7% |
| `weak_score`（Qwen） | 0／0.3／0.5／0.7 | 0.3 | 英文 14.8% → 12.1%，三個值相同 |
| Qwen 上下文與邊界 | `context_tokens` 0／4 × `window_pad_ms` 500／1000 | 4／1000（不變） | 見上面第 9 點 |
| `hybrid` 的門檻 | Qwen 分數 0.3／0.5／0.7／0.9 | CTC < 0.3、Qwen ≥ 0.5 | 用兩個對齊器各自的 dev 結果離線模擬 |
| Whisper 注意力對齊器偏移 | — | −110 ms | 關掉吸附時的偏差中位數（中文 −105、英文 −180、混合 −140） |

這些值都落在「附近幾個值結果差不多」的平坦區間裡，沒有哪一個是靠精細調整才得到的。

## 決定

- **`balanced`（預設）＝ `ctc`。** 只用 Apache-2.0 的權重、不需要額外套件、任何預設安裝都能重現；
  規格 §10.4 的目標就是以這個設定檔評測。
- **`cpu-lite` ＝ `whisper-attn`。** 不需要多下載對齊模型（省 1.6 GB），計算量最小；準確度明顯較差，文件會寫清楚。
  CI 與整合測試用這個設定檔。
- **`gpu-quality` ＝ `auto`**：裝了 `qwen-asr` 就用 `hybrid`，否則退回 `ctc`（`kf doctor` 會提示）。
  `hybrid` 在 CPU 上也跑得動（Qwen 約每分鐘音訊 5 秒），想要更好的英文與混合語言結果的人可以在任何設定檔加上
  `--set align.aligner=hybrid`。
- **Qwen 是選用套件（`uv sync --extra qwen`），不是核心相依。**（後記：它的相依 `soynlp` 是 GPL-3.0，已在安裝時排除，見 ADR 0012。） `qwen-asr` 把 `transformers`、`accelerate` 釘在特定版本，
  還會帶進 gradio、flask 等示範用的套件；放進核心相依會讓每個使用者都背這些限制。
  因為 lock 檔要同時滿足這個 extra，目前整個專案鎖定在 `transformers 4.57.6`。
- **`ctc-mms` 不是任何設定檔的預設。** MMS 的權重是 CC-BY-NC，使用者必須用 `kf models download mms-fa --accept-license`
  明確同意後才會下載。

## 沒有採用的做法

- **把 Qwen3-ForcedAligner 當成唯一的預設**（規格的建議）：在這份測資上它對中文並沒有比 CTC 好（5.9% 對 3.9%），
  又需要額外套件；它的價值在英文詞，所以放在 `hybrid` 裡。
- **整首歌一次強制對齊**：留作消融實驗（`align.coarse=global`），結果見評測報告。
- **把起音點直接放進 Viterbi 的轉移分數**（讓 CTC 與起音偵測聯合決定位置）：有機會再改善英文詞偏晚與混雜行的問題，
  但需要改動介面讓對齊器拿到特徵；先以「事後補救沒有證據的字」取代，留待之後評估。

## 已知沒有解決的問題

- 中英混雜的行仍然是最弱的一環（`ctc` 13.6%、`hybrid` 10.6%）：英文模型在拉長的中文母音上會輸出零星的字母，
  行尾的英文詞有時被往前吸過去。
- 合成測資裡有一類第三聲的字（例如「雨」）被聲碼器算繪成「開頭 0.15 秒、中間靜音、結尾才是主體」，
  對齊器會把它放在主體的位置，比標準答案晚約 0.6 秒。這是測資的瑕疵，但測資已經定稿，沒有為此修改（見 ADR 0007）。
- 所有數字都來自合成歌聲；真實歌曲上的表現沒有量測過（專案不能附帶有版權的歌，見 `bench/real/README.md`）。

## `ctc-mms`（MMS 單一多語模型）的結果

`ctc-mms` 用 Meta MMS 的強制對齊模型（羅馬拼音輸入，一個模型涵蓋所有語言）取代「中文 wav2vec2 + 英文 wav2vec2」這一對。
它的權重是 **CC-BY-NC-4.0**，所以不論結果如何都不會是預設值；評測它是為了知道「授權比較嚴的那個選項」到底差多少。

**dev 分組（校正前，`lag = 0`，2652 個 token；紀錄在 `bench/_runs/tune/mms-dev-1.json`）：**

| | 中位數 | P95 | >150 ms | bias |
|---|---:|---:|---:|---:|
| 中文，不吸附 | 22 ms | 118 ms | 4.9% | +20 ms |
| 英文，不吸附 | 56 ms | 275 ms | 9.7% | +50 ms |
| 混合，不吸附 | 28 ms | 289 ms | 8.4% | +22 ms |
| 全部，不吸附 | 33 ms | 239 ms | 7.4% | +29 ms |
| 全部，吸附 | 21 ms | 231 ms | 7.3% | +15 ms |

依照與其他對齊器相同的流程，把「不吸附」時的 bias 寫成這個模型的延遲修正：漢字 20 ms、其他 50 ms
（`adapters/aligners/ctc.py` 的 `_LAG_S`）。**校正之後沒有再跑一次 dev**——當時 test 分組的評測已經排定，
而這個對齊器不是任何設定檔的預設，所以校正後的第一次量測就是 test 分組上的那一次。

**test 分組（校正後，取自 [benchmark-report.md](../benchmark-report.md)；>150 ms 的比例）：**

| | 0 dB | 5 dB | 10 dB | 20 dB |
|---|---:|---:|---:|---:|
| 中文：`ctc`（預設）／`ctc-mms` | 7.0% ／ 5.2% | 3.7% ／ 2.0% | 2.8% ／ 2.4% | 3.5% ／ 2.3% |
| 英文：`ctc` ／ `ctc-mms` | 4.3% ／ 3.8% | 3.2% ／ 4.1% | 5.1% ／ 4.7% | 6.6% ／ 3.6% |
| 混合：`ctc` ／ `ctc-mms` | 14.1% ／ 9.2% | 9.8% ／ 4.9% | 8.7% ／ 4.6% | 9.3% ／ 9.5% |

老實說：**在這份測資上，`ctc-mms` 在 12 格裡有 10 格比預設的 `ctc` 好，中英混合的行尤其明顯**（單一模型不會有兩個模型互相干擾的問題）。
它沒有成為預設值，純粹是因為授權：預設組合必須讓使用者可以放心做任何用途。
不介意非商業授權的人可以這樣用：

```bash
kf models download mms-fa --accept-license
kf run my-song.kfproj --set align.aligner=ctc-mms
```

它的信心度比較不可靠（中文 10 dB 的 AUROC 0.77，預設的 `ctc` 是 0.93）；原因沒有調查。
