# ADR 0009：Web App 的架構

- 狀態：已採用
- 日期：2026-11-21

## 背景

規格 §6 要求一個本機 Web App：專案列表、新增精靈、處理進度（SSE、可取消）、編輯器（JASSUB 預覽、歌詞面板、
可拖曳的時間軸、打點模式、重新對齊、復原／重做、自動儲存與衝突偵測、主題編輯器、中英文介面）以及匯出。
API 的形狀是「建議」，以下是實際採用的設計與理由。

## 決定

### 後端（`engine/karaforge/server/`）

- **專案就是資料夾。** 伺服器的「工作區」是一個放著 `*.kfproj` 的資料夾（`kf serve --workspace`，預設是目前的資料夾），
  專案 id 就是資料夾名稱去掉副檔名。沒有資料庫，CLI 做的專案在 Web 裡直接看得到，反過來也一樣。
- **一次只跑一個工作。** 處理一首歌會把所有核心用滿，同時跑兩個只會兩個都變慢；工作排進佇列，由單一工作執行緒依序執行，
  排隊中與執行中的工作都可以取消（引擎在階段之間與階段內檢查取消旗標）。工作狀態只放在記憶體裡——
  伺服器重啟後正在跑的工作就沒了，但各階段的快取還在，重新按一次「處理」會從中斷的地方繼續。
- **事件用 SSE。** `/api/events` 送出兩種事件：工作狀態（進度有節流）與「某個專案被改了」。
  工作執行緒透過 `loop.call_soon_threadsafe` 把事件交給每個訂閱者自己的有界佇列，跟不上的訂閱者丟掉最舊的事件而不是卡住工作。
- **儲存要帶 revision。** `PUT /api/projects/{id}` 必須附上編輯所依據的 revision，與磁碟上的不同就回 409、什麼都不寫。
  另一個視窗或背景工作改過專案時，編輯器不會默默蓋掉它。
- **預覽與匯出同源。** `POST /api/projects/{id}/preview` 接受一份「尚未儲存的」專案內容，
  用與匯出完全相同的排版引擎與 ASS 產生器回傳腳本與它需要的字型清單。
- **會動到文字規則的編輯在伺服器做。** 改一行歌詞後要保留哪些字的時間，取決於 tokenizer；
  為了不在 TypeScript 裡再寫一份 tokenizer，這個操作是 `POST /api/tools/retokenize`（無狀態：送一行進去、回一行出來）。
- **時間軸要的資料按需產生並快取**：人聲軌的波形峰值、頻譜圖（PNG 圖磚）、影片縮圖都在第一次被要求時才計算。
- 前端打包後的靜態檔由同一個 FastAPI 提供，未知路徑退回 `index.html`，所以 `kf serve` 一個指令就能用。
- 伺服器沒有登入機制，預設只聽 `127.0.0.1`；指定其他位址時 CLI 會印出警告。

### 前端（`web/`）

- **React 19 + TypeScript（strict）+ Vite；狀態用 zustand，伺服器資料用 TanStack Query。** 沒有使用 UI 元件庫，樣式是一份純 CSS。
- **編輯邏輯是純函式。** `editor/doc.ts` 的每個操作（移動開始時間、拖曳、微調、打點、斷行、合併…）都只改傳進來的文件，
  可以直接當成 immer 的 recipe，也因此可以不靠瀏覽器做單元測試。規則集中在這裡：
  例如「前一個字原本貼著這個字，就讓它的結束時間跟著走」。
- **復原／重做用 immer patches**（`editor/history.ts`）。帶有相同 `mergeKey` 的連續編輯（拖曳、按住方向鍵、在輸入框打字）
  在 0.8 秒內會併成一步，所以一次拖曳按一次復原就回去。
- **自動儲存**：編輯後 1 秒沒有新的編輯就送出；送出期間又有編輯會再送一次；遇到 409 就停止儲存並顯示衝突，
  直到使用者重新載入。背景工作（處理、重新對齊）執行期間編輯器是唯讀的，工作結束後自動載入新的文件。
- **播放時鐘是音訊，不是影片。** 伴唱／原唱／只聽人聲各有一個 `<audio>`，選中的那個負責播放並作為主時鐘；
  影片元素（靜音）、字幕、時間軸都跟著它。這樣切換音軌不會跳掉位置，純音訊的專案也用同一套流程。
- **JASSUB 用 canvas 模式、由編輯器告訴它現在幾秒**（`manualRender`），而不是讓它自己跟著 `<video>`——
  理由同上。腳本用到的字型在第一個影格之前就載入：JASSUB 對「只是可用」的字型是在某個影格需要時才去抓，
  而那個影格會先畫不出字，暫停時就一直是空的。
- **時間軸是一個自己畫的 `<canvas>`**（尺規、波形或頻譜圖、起音點、每個字一個方塊、播放頭）。
  沒有採用 wavesurfer 之類的元件：需要的互動（方塊本體與左右邊界的拖曳、吸附起音點、兩排交錯的字、與復原系統整合）
  用現成元件反而要繞路；幾何計算（時間↔像素、命中測試、波形欄位）是純函式，有單元測試。
- **介面文字**是兩個型別相同的字典（`i18n/zh-TW.ts`、`i18n/en.ts`），TypeScript 保證兩邊的鍵一致，
  測試再檢查每個字串的佔位符相同。伺服器的錯誤本來就同時帶有中英文訊息與建議。
- `window.karaforge`（`seek`／`now`／`play`／`pause`）是給進階使用者與瀏覽器測試用的小型 console API。

### 測試

| 層 | 工具 | 內容 |
|---|---|---|
| 伺服器 | pytest + FastAPI TestClient | API 的每個端點、工作佇列、事件匯流排；另有透過真實 socket 的 SSE 與 Range 測試 |
| 前端邏輯 | Vitest | 編輯操作、歷史、store（自動儲存與衝突）、播放時鐘、時間軸幾何、i18n |
| 前端元件 | Vitest + Testing Library | 專案列表、新增精靈、處理進度頁（`fetch` 以假伺服器取代） |
| 端對端 | Playwright（Chromium） | 對真正的伺服器操作：編輯、拖曳、打點、匯出、主題、影片同步，以及**預覽與匯出影片的影格比對** |

端對端測試用的工作區由 `web/e2e/make_workspace.py` 建立，不需要任何模型（只需要 ffmpeg）；
需要真實模型的整條流程（上傳 → 處理 → 編輯 → 重新對齊）是另一個要明確開啟的測試（`KARAFORGE_E2E_MODELS=1`）。

## 沒有採用的做法

- **WebSocket**：只需要伺服器往瀏覽器單向推送，SSE 夠用而且瀏覽器會自己重連。
- **把工作交給外部佇列（Celery／RQ）**：單機單使用者的工具不需要再多一個服務。
- **在瀏覽器裡用 WebAudio 混音**（伴奏＋可調音量的導唱）：三個 `<audio>` 元素切換已經滿足規格，
  也不必把整首 WAV 解碼進記憶體；匯出時的「伴奏＋導唱」由 ffmpeg 混音。
- **跨來源隔離（COOP／COEP）標頭**：加上後 JASSUB 可以多執行緒，但會連帶限制頁面載入其他來源的資源。
  目前單執行緒模式在瀏覽器測試中可以正常預覽；預覽的影格率沒有量測過，所以這是「還沒有需要」而不是「量過不需要」。

## 後果與限制

- 伺服器重啟會遺失工作佇列與正在執行的工作（不會遺失資料）。
- 兩個瀏覽器分頁同時編輯同一個專案時，後儲存的那個會看到衝突並需要重新載入；沒有做即時協同編輯。
- 預覽需要 WebAssembly、OffscreenCanvas 與 Web Worker（JASSUB 的說明文件列出的最低版本是 Chrome 85、Safari 17、Firefox 105）；
  預覽無法啟動時編輯器的其他部分仍然可用，並顯示原因。
- 端對端測試只在 Chromium 上執行過。
