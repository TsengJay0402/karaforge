# ADR 0003：Token 模型——標點附著、未對齊為 null、逐字與逐詞

- 狀態：已採用
- 日期：2026-11-20

## 背景

規格要求「中文以字為單位、英文以詞為單位、中英混合要正確處理」，`project.json` 的 token 只有一個 `text` 欄位。
需要決定：標點與空白放哪裡、還沒對齊的 token 怎麼表示、手動指定的讀音放哪裡。

## 選項

1. 標點與空白各自成為 token。行文字可以完整還原，但會出現一堆「不需要時間」的 token，編輯器與對齊都要特別處理。
2. token 只存核心文字，標點另外用 `prefix`／`suffix` 欄位。乾淨，但偏離規格的單一 `text`。
3. **標點與空白附著在相鄰 token 的 `text` 上**：收尾標點與其後的空白附在前一個 token，開頭標點（「（“ 等）附在後一個 token。

## 決定

採用選項 3。

- 把一行所有 token 的 `text` 串起來就是原本的那一行（空白正規化後），所以 LRC／ASS 等格式的往返不需要額外資訊。
- 需要「核心文字」的地方（對齊、讀音、比對）用 `karaforge.text.tokenize` 現場拆出 `core`。
- 單位：漢字一字一 token；假名一個一 token（小假名與長音併入前一個）；諺文一個音節一 token；
  其他文字以「詞」為單位（`don't`、`3.14` 視為一個詞；連字號後可以斷開）。
- 只有標點的一行會得到一個 `kind = NONE` 的 token：照樣顯示，但不送進對齊器。
- 還沒對齊的 token，`start_ms`／`end_ms` 都是 `null`（兩者必須同時有或同時沒有）。
  `locked` 的 token 一定要有時間。
- 歌詞檔的 `字{讀音}` 變成該 token 的 `ruby`，並標記 `ruby_source = "manual"`；
  對齊與自動讀音都把手動讀音當成事實。
- 因為時間必須成對修改，而模型開啟了 `validate_assignment`，改時間一律透過 `Token.retimed()` 產生新的 token。

## 後果

- 填色時，附著的標點會跟著該字一起被填色（符合一般 KTV 字幕的觀感）。
- 以音節為單位的 token（例如從增強型 LRC 匯入的 `to` `ge` `ther`）也能表示：token 之間沒有空白，
  排版引擎不會在它們中間斷行。
- 需要核心文字的程式要多呼叫一次 tokenizer；成本很低，而且集中在少數幾個函式。
