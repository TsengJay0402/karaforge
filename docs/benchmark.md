# 對齊評測

KaraForge 的核心價值是「自動對齊有多準」，所以這份評測是專案最重要的品質證據。
本文件說明評測資料、指標的定義、怎麼重現、調校流程，以及結果的摘要與解讀。實測數字的原始報告有兩份，
都是 `kf bench` 產生後**原樣**複製進來的，沒有人工修改：

| 報告 | 內容 | 演算法版本 |
|---|---|---|
| [`benchmark-report.md`](benchmark-report.md) | 完整矩陣：主要設定、消融實驗、錨點實驗、五種對齊器的比較（120 個音檔 × 12 種設定） | 7（commit `f56d855`） |
| [`benchmark-report-anchors.md`](benchmark-report-anchors.md) | 主要設定與錨點實驗（新、舊兩種錨點處理方式並列，外加「同一批字鎖定前後」的配對表） | 8（commit `0ce6cbf`） |

兩份報告的機器可讀版本與每個 token 的預測值在 [`bench/reports/`](../bench/reports/)。
報告裡記錄的 commit 是公開前改寫 git 歷史以前的編號：`376ecb5`＝現在的 `f1585cf`、`8f43048`＝`0ce6cbf`、`3dd0d6a`＝`b7963bf`
（見 [REPORT.md](../REPORT.md) 第 7 節「關於 commit 編號」）。
第 8 版只改了「有鎖定字時」的行為：沒有錨點的設定在兩次執行中每一個 token 的時間都完全相同（已逐一比對 120 個音檔），
所以第一份報告裡沒有錨點的數字對目前的程式仍然成立。

## 一眼看懂

```bash
uv sync --extra cpu --group bench     # 評測需要的額外套件（TTS、聲碼器）
kf models download --profile balanced
kf bench                              # 合成測資 test 分組、balanced 設定檔，含錨點實驗
kf bench --ablation --aligner whisper-attn --aligner qwen --aligner hybrid   # 加上消融實驗並比較對齊器
```

第一次執行會先合成測資（約 15 分鐘），之後每個音檔的人聲分離與語音辨識結果都會被快取，
換一種設定重跑只需要重新對齊。

## 資料

| 套件 | 內容 | 用途 |
|---|---|---|
| `synthetic`／`test` | 中文、英文、中英混合各 10 首 × 訊噪比 0／5／10／20 dB＝120 個音檔 | **報告裡的所有數字** |
| `synthetic`／`dev` | 每種語言 4 首 × 4 種訊噪比＝48 個音檔 | 調整參數，不出現在報告裡 |
| `synthetic`／`smoke` | 1 首 | 確認流程能跑 |
| `real` | 你自己放進 `bench/real/songs/` 的歌與人工校正檔 | 真實歌曲（不進版控），見 [`bench/real/README.md`](../bench/real/README.md) |

合成測資怎麼做、為什麼這樣做、有哪些侷限，寫在 [ADR 0007](adr/0007-synthetic-benchmark.md)。重點：

- 歌聲是 Kokoro TTS 逐字合成後，用 WORLD 聲碼器改成旋律的音高與節拍上的時值；有長音、vibrato、快速段落、
  連音（字與字之間沒有靜音）、行內換氣、超過 8 秒的間奏、重複的副歌與對唱。
- 伴奏用 numpy 合成（鼓、bass、和弦、前奏與間奏的旋律），以四種訊噪比混音。
- 每個字的標準答案是它在乾聲裡「RMS 包絡第一次達到該字最大值 5%」的時間。

## 指標

所有指標都以 token（一個漢字或一個英文詞）為單位，定義在 `bench/kfbench/metrics.py`：

| 指標 | 定義 |
|---|---|
| 起始時間誤差 | `|預測的開始時間 − 標準答案|`。報告中位數、P90、P95。 |
| bias | 「預測 − 標準答案」的中位數；正值表示系統偏晚。 |
| 需人工修正比例 | 起始時間誤差超過 **150 ms** 的 token 比例：使用者大約要動手修幾成的字。 |
| wrong line（行對應錯誤） | 預測的開始時間離「別的行」的真實時間範圍比離自己那一行還近的 token 比例。 |
| 行尾結束誤差 | 每行最後一個字的結束時間誤差（長音處理的成效）。 |
| 信心度 AUROC | 用 `1 − confidence` 來找出「需人工修正」的 token，排序品質有多好（0.5＝沒有用，1.0＝完美）。 |
| 檢查信心最低 k% 找到的問題比例 | 使用者只檢查信心最低的 k% token，能找到多少比例的問題。 |
| 處理時間 | 各階段實際計算的秒數，換算成「每分鐘音訊需要幾秒」。 |

錨點實驗裡被鎖定（設成標準答案）的 token 不計入任何指標，否則等於把答案算成系統的功勞。

### 錨點實驗

模擬「使用者修正幾個字，其餘自動變準」：

1. 先正常對齊一次。
2. 選出 5% 的 token，把它們設成標準答案並鎖定（`locked`）。有兩種選法：
   - `anchors-random`：隨機選（種子由歌曲與設定名稱決定，可重現）。**規格的目標指的是這一種。**
   - `anchors-lowconf`：選信心度最低的 5%——也就是編輯器會標紅、使用者實際上最先去修的那些字。
3. 重新對齊（只會重算錨點之間的區段），用其餘 95% 的 token 計算指標。

### 消融實驗

`--ablation` 會對主要設定另外跑：

| 名稱 | 改動 | 想回答的問題 |
|---|---|---|
| `no-coarse(regions)` | 不用語音辨識，行的時間窗只依人聲活動區段按字數分配 | 粗對齊（ASR 行層級錨定）有多少貢獻？ |
| `no-coarse(global)` | 完全不切時間窗，整首歌一次強制對齊（只有沒有長度限制的對齊器能跑） | 「一行一個時間窗」是否避免了誤差累積？ |
| `no-onset-snap` | 關掉起音點吸附 | 精修的吸附有多少貢獻？ |
| `no-weak-rescue` | 不把「對齊器沒有證據」的字移到附近的起音點 | 補救機制有多少貢獻？ |
| `no-long-note` | 行尾不延長到人聲消失 | 只影響結束時間 |

錨點實驗固定多跑一個 `anchors-random-5% (v7 handling)`：用完全相同的錨點，但以第 7 版的方式處理（`align.anchor_context=false`）。

## 規格的目標

`balanced` 設定檔、訊噪比 10 dB 的中文測資（規格 §10.4）：

| 指標 | 目標 |
|---|---:|
| 起始時間誤差中位數 | ≤ 60 ms |
| 起始時間誤差 P95 | ≤ 250 ms |
| 需人工修正比例（> 150 ms） | ≤ 10% |
| 隨機鎖定 5% 錨點後的需人工修正比例 | ≤ 5% |

報告的第一張表就是這四項的實測值與「達成／未達成」。沒達成就照實寫沒達成：門檻、測資與指標的定義都不會為了過關而改。

## 結果摘要

以下是從兩份原始報告與 `bench/reports/*/tokens.json.gz` **整理**出來的摘要（把四種訊噪比合併計算）；逐格的數字請看原始報告。
test 分組，30 首歌 × 4 種訊噪比＝120 個音檔、7480 個 token。

### 與規格目標的對照（`balanced`，中文，10 dB，747 個 token）

| 指標 | 目標 | 實測 | |
|---|---:|---:|---|
| 起始時間誤差中位數 | ≤ 60 ms | 11 ms | 達成 |
| 起始時間誤差 P95 | ≤ 250 ms | 86 ms | 達成 |
| 需人工修正比例（> 150 ms） | ≤ 10% | 2.8% | 達成 |
| 隨機鎖定 5% 錨點後 | ≤ 5% | 3.0%（第 8 版）；4.2%（第 7 版） | 達成 |

第四項要一起看下面的「錨點實驗的教訓」：兩個版本都低於 5%，但那不代表錨點有幫助。

### 各對齊器（誤差 > 150 ms 的比例；括號內是中位數／P95，單位 ms）

| 設定 | 中文 | 英文 | 中英混合 | 全部 |
|---|---:|---:|---:|---:|
| `balanced`（`ctc`，預設） | 4.3%（12／124） | 4.8%（17／147） | 10.5%（16／402） | 6.6%（14／210） |
| `hybrid`（CTC + Qwen，選用） | 3.9%（12／113） | 4.0%（12／121） | 8.9%（14／395） | 5.7%（13／195） |
| `ctc-mms`（非商業授權） | 3.0%（12／93） | 4.1%（12／118） | 7.0%（14／270） | 4.7%（12／140） |
| `qwen` | 12.8%（14／576） | 10.7%（13／475） | 20.8%（20／1235） | 15.0%（15／790） |
| `whisper-attn`（`cpu-lite` 用的對齊器，搭配 Whisper small） | 17.9%（35／303） | 27.2%（40／817） | 20.8%（42／689） | 21.2%（39／569） |

- 預設的 `ctc` 不是最準的：授權受限的 `ctc-mms` 在每一種語言上都比較好，選用的 `hybrid` 也略好。預設值是依授權與相依套件決定的（見 ADR 0006）。
- 中英混合的歌詞是明顯的弱點，P95 是單一語言的三倍。
- `cpu-lite` 實際使用的是更小的 Whisper base，沒有在這份測資上跑過；它只會比表中的 `whisper-attn` 更差。

### 消融實驗（`balanced`；誤差 > 150 ms 的比例，括號內是中位數）

| 設定 | 中文 | 英文 | 中英混合 | 全部 |
|---|---:|---:|---:|---:|
| 完整 | 4.3% | 4.8% | 10.5% | 6.6%（14 ms） |
| 不用語音辨識做行層級錨定（`no-coarse(regions)`） | 22.2% | 20.7% | 26.9% | 23.5%（23 ms） |
| 完全不切時間窗，整首一次對齊（`no-coarse(global)`） | 4.5% | 4.3% | 10.2% | 6.5%（14 ms） |
| 關掉起音點吸附 | 4.3% | 3.8% | 11.3% | 6.6%（23 ms） |
| 關掉「沒有證據的字」的補救 | 4.5% | 5.1% | 11.1% | 6.9%（15 ms） |
| 關掉行尾長音 | 與完整相同（只影響結束時間） | | | |

照實說這些數字代表什麼：

- **用語音辨識把每一行定位，是整個系統最重要的一步**（23.5% → 6.6%）。
- **「一行一個時間窗」在這份測資上沒有量到好處。** 對沒有長度限制的 CTC 對齊器來說，整首歌一次對齊的結果（6.5%）與逐行對齊（6.6%）沒有差別。
  規格擔心的「整首一起對齊時誤差越滾越大」在這些 30–60 秒的合成歌曲上沒有發生。時間窗對有長度限制的對齊器（Whisper 30 秒）仍然是必要的，
  而且是錨點重對齊與「只重新對齊某幾行」的基礎；但「它讓 CTC 對得更準」這個說法，我們沒有證據。真實長度（3–5 分鐘）的歌會不會不同，沒有量過。
- **起音點吸附改善的是精細度，不是出錯率**：中位數從 23 ms 降到 14 ms，但誤差超過 150 ms 的比例不變（英文甚至略差）。
- 補救機制的貢獻很小（6.9% → 6.6%）。

### 錨點實驗的教訓

錨點實驗模擬「使用者修了幾個字，其餘的字跟著變準」：把 5% 的字設成標準答案並鎖定，再重新對齊。
下表把**同一批沒有被鎖定的字**在鎖定前後配對（原始報告的「錨點對其餘 token 的影響」一節；test 分組，7116 個 token）：

| 錨點處理方式 | 選法 | 鎖定前需修正 | 鎖定後需修正 | 修好的字 | 弄壞的字 |
|---|---|---:|---:|---:|---:|
| 第 7 版 | 隨機 5% | 6.5% | **7.7%** | 76 | 159 |
| 第 8 版（目前） | 隨機 5% | 6.5% | 6.1% | 42 | 12 |
| 第 8 版（目前） | 信心度最低的 5% | 5.2% | 4.8% | 48 | 18 |

第 8 版依語言分開看（隨機 5%）：中文 4.2% → 4.3%（修好 4、弄壞 8），英文 4.9% → 4.3%，中英混合 10.4% → 9.5%。

事情的經過，照實記錄：

1. 第 7 版在凍結前**沒有在 dev 分組上跑過錨點實驗**（只有單元測試驗證「鎖定的字不會被移動」）。這是流程上的疏漏。
2. test 分組的第一次評測顯示：鎖定錨點之後，其餘的字**變差**了，英文最明顯。規格的目標格（中文 10 dB）雖然是 4.2% ≤ 5%「達成」，
   但那一格在沒有錨點時是 2.8%——數字低於門檻，方向卻是錯的。
3. 回到 dev 分組重做同樣的實驗，看到同樣的現象（7.7% → 9.2%），找到兩個原因並修正（見 [alignment.md](alignment.md) 的「錨點重對齊」）：
   有鎖定字的行只用鎖定的字來猜時間窗（一個字假設 0.4 秒，慢歌的行尾因此被切掉）；以及音訊在鎖定字的邊緣被切開，對齊器聽不到完整的音節。
   修正只在 dev 上調整與驗證（dev：7.7% → 7.0%，弄壞的字從 66 個降到 7 個）。
4. 之後才在 test 分組上量第 8 版，就是上表。這次量測包含用同一批錨點重跑的第 7 版行為，結果與第一次評測逐字相同，所以兩者可以直接比較。

要誠實面對的幾點：

- 第 8 版是**看過 test 分組的結果之後**才做的修正。雖然調整只用 dev，但「知道哪裡有問題」這件事本身來自 test，嚴格來說這已經不是一次盲測。
- 修正之後錨點**不再有害**，但幫助有限：整體只少了 0.4 個百分點，中文甚至是持平到略差（弄壞 8 個、修好 4 個）。
  「修三個字，其餘自動變準」這句話，目前的數據只支持到「修三個字，其餘大致不受影響，英文與混合歌詞會好一點」。
- 這個實驗對舊方法其實是**偏袒**的：錨點的結束時間用的是標準答案，而舊方法把鎖定字的結束時間當成硬性邊界。
  真實使用時，使用者改的是開始時間，結束時間常常是舊的對齊結果——舊方法在那種情況下會更差，這份測資量不到。
- 剩下的失敗案例（dev 上逐一看過）主要是：對齊器把錨點後面的字放到錯的地方時，錨點沒有被用來「釘住」路徑。
  合理的下一步是把鎖定字的位置直接變成 CTC 動態規劃裡的限制條件。

## 調校流程（只用 dev 分組）

對齊器各有固定的偏差（例如 CTC 模型的輸出尖峰落在音節開始之後一小段時間），精修的參數也需要選值。
這些數字**只用 dev 分組決定**，流程如下，決定之後才第一次在 test 分組上執行：

1. 量測每個對齊器的原始偏差：關掉吸附與各種補救後跑 dev，
   `python -m kfbench.tune --aligner <名稱> --set align.onset_snap=false --set align.lead_ms=0 --set align.weak_score=0`，
   表中的 `bias` 就是該對齊器的偏差，寫進該 adapter（CTC 依模型分別扣除，Whisper 寫在 `lead_ms`）。
2. 在 dev 上比較吸附距離等參數（`--grid align.onset_snap_ms=40,60,80`），選定後寫進預設值。
3. 在 dev 上比較各對齊器，決定各設定檔的預設對齊器。
4. 凍結。之後才跑 `kf bench --split test …` 產生報告。

`kfbench.tune` 是專門用來調校的工具：它沿用工作專案裡分離與辨識的快取，同一首歌的每一種參數組合只重做對齊，
所以一格參數只要幾秒；而且它**拒絕在 test 分組上執行**。

實際試過的值、選定的數值與 dev 上的比較表都記錄在 [ADR 0006](adr/0006-aligner-choice.md)。

## 輸出

`kf bench` 把三個檔案寫到 `bench/_runs/reports/<套件>-<分組>-<設定檔>/`（或 `--output` 指定的資料夾）：

- `report.md`：給人看的報告。
- `results.json`：同樣的數字，機器可讀。
- `tokens.json.gz`：每個 token 的預測與標準答案，可以拿來做進一步分析。

工作用的專案（含分離後的音軌與各階段快取）在 `bench/_runs/work/`，可以用 `kf serve` 打開來聽、來看對齊結果。

### 只量一首歌

合成歌曲都附有 `truth.json`（每個字真正的時間），所以任何一個處理過的專案都可以單獨拿來比，指標的定義與 `kf bench` 相同：

```bash
python scripts/compare_with_truth.py examples/demo/project.json tests/fixtures/songs/zh-2000/truth.json
```

它也會比較歌詞文字本身（字元錯誤率），用來看沒有歌詞時語音辨識草稿錯了多少。
`scripts/join_songs.py` 可以把幾首合成歌曲接成一首正常長度的歌，連同歌詞與標準答案一起輸出。

## 解讀時要注意

- 合成歌聲比真人演唱規律得多（咬字清楚、沒有轉音與和聲），伴奏也比真實歌曲單純。
  合成測資上的數字應該視為**接近上限的參考值**，不是真實歌曲上的保證。
- 0 dB 與 5 dB 的結果主要反映人聲分離的品質；20 dB 則接近「直接對乾聲對齊」。
- 標準答案對「一個字從哪裡開始」採用能量門檻的定義；對於以鼻音或摩擦音開頭的字，
  人耳感覺到的起點可能與這個定義相差 10–30 ms。
